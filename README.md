# Lead Service

Сервис приёма и отправки заявок партнёрам на Laravel, MySQL и Redis.

## Требования

- Docker Engine
- Docker Compose
- GNU Make

## Запуск проекта

Все команды make выполняются из корня проекта — каталога с Makefile и docker-compose.yml.

## 1. Настройка окружения
Настройка окружения

При первом запуске ```make build ``` автоматически создаёт src/.env из src/.env.example, если файл отсутствует.

Перед запуском проверь настройки подключения к БД, порты и остальные параметры окружения в src/.env.

## 2. Запуск контейнеров:

   ```bash
   make up
   ```

## Тестовые данные

Для создания тестового партнёра выполни:

- make seed

Сидер создаёт партнёра demo-partner и выпускает API-токен через PartnerTokenService. При первом выпуске токен выводится в консоль. Сохрани его: в базе хранится только SHA-256-хеш секрета, восстановить исходный токен невозможно.

Повторный запуск сидера не должен создавать дубликат партнёра или выпускать новый токен, если существующий токен уже настроен.

Тестовый адрес партнёра https://example.com/webhook является примером и не предназначен для реальной доставки заявок. Для проверки доставки настрой доступный HTTP endpoint в параметрах партнёра.

## Основные возможности

- Приём и хранение заявок.

- Хранение партнёров и параметров их подключения.

- Асинхронная отправка заявок партнёрам через HTTP.

- Сохранение полученного от партнёра request_id.

- Обработка ошибок доставки и повторные попытки.

- Приём вебхуков с результатами обработки заявок.

- Авторизация партнёров по API-токенам.

- Валидация входящих данных.

- Сохранение истории вебхуков.

- Идемпотентная обработка повторных вебхуков без дублирования начислений.

### Структура базы данных: ###
- leads — заявки клиентов.
- partners — партнёры и параметры их подключения.
- lead_deliveries — отправки заявок партнёрам, статус, request_id, число попыток и время отправки.
- webhook_events — история полученных вебхуков и данные для идемпотентности.
- delivery_revenues — доход по отправкам.

Схема разделяет заявки (`leads`), партнёров (`partners`),
отправки заявок (`lead_deliveries`), события вебхуков (`webhook_events`)
и начисления дохода (`delivery_revenues`), 
чтобы каждая таблица отвечала за отдельную сущность и не дублировала данные других таблиц.
Для связей используются внешние ключи 
с ограничением удаления связанных записей (`RESTRICT`), 
что защищает историю отправок, вебхуков и начислений от случайной потери. 
Для денежных сумм и счётчиков попыток выбраны целочисленные типы, 
а для дат — `DATE`, `TIMESTAMP` и стандартные временные поля Laravel в зависимости
от назначения. Поле `payload` имеет тип `JSON`,
чтобы сохранить полный исходный набор данных заявки или вебхука, включая поля,
которые не вынесены в отдельные столбцы. Индексы по телефону, email, статусу,
партнёру и идентификатору отправки ускоряют поиск заявок и обработку вебхуков. 
Уникальные ограничения не позволяют создать несколько отправок одной заявки одному партнёру,
повторно использовать идентификатор события партнёра
или начислить доход одной отправке более одного раза. 
История вебхуков хранится отдельно от текущего статуса отправки, 
что позволяет отслеживать результат обработки и обеспечивать идемпотентность 
повторных уведомлений.

### Идемпотентность обработки вебхуков

Идемпотентность обеспечивает защиту от повторной обработки 
одного и того же вебхука и повторного начисления дохода.

При получении POST /api/webhook/status сервис:
Валидирует входные данные и определяет партнёра по Bearer-токену.
Ищет отправку заявки по request_id. Если отправка не найдена, возвращает 404.
Сохраняет событие вебхука в таблице webhook_events, включая идентификатор отправки,
исходные данные и результат обработки.
Обрабатывает событие и обновляет статус отправки в рамках транзакции БД.
Сохраняет доход в delivery_revenues. Уникальное ограничение по delivery_id
не позволяет создать несколько начислений дохода для одной отправки.
При повторном получении уже обработанного события не начисляет доход повторно.
Дополнительную защиту обеспечивают уникальные ограничения БД на идентификатор 
события партнёра и на связь дохода с отправкой. 
Транзакция позволяет сохранить согласованность изменений при ошибках обработки.
Таким образом, повторная доставка вебхука не приводит к повторному начислению дохода.

### API ###

### Создание заявки ###

POST /api/leads

Заголовки:
```bash
Content-Type: application/json
Accept: application/json
```

Пример тела запроса:
```bash
{
"first_name": "Ivan",
"last_name": "Petrov",
"birth_date": "1990-05-15",
"phone": "+79991234567",
"amount": 10000,
"term": 12,
"passport": {
"series": "1234",
"number": "567890",
"issued_by": "Test department",
"issued_date": "2015-06-10",
"division_code": "123-456"
},
"address_registration": {
"region": "Краснодарский край",
"city": "Краснодар",
"street": "Тестовая",
"house": "1"
},
"address_residence": {
"region": "Краснодарский край",
"city": "Краснодар",
"street": "Тестовая",
"house": "1"
},
"sub_ids": {
"sub_id_1": "test-sub-id-1"
}
}
```
amount заявки указывается целым числом в копейках.

При успешном приёме возвращается HTTP 202 Accepted:

```bash
{
"message": "Lead accepted",
"lead_id": 1,
"deliveries_queued": 1
}
```

Заявка сохраняется в базе данных, после чего для каждого активного партнёра ставится задача доставки в очередь.

Ответ 202 Accepted означает, что заявка принята в обработку, а не то, что партнёр уже подтвердил её получение.

Основные ответы:

- 202 — заявка принята.

- 422 — данные не прошли валидацию.

2. Доставка партнёру

Фоновая задача отправляет заявку активному партнёру через HTTP-клиент.

Для доставки сохраняются:

- идентификаторы заявки и партнёра;

- статус доставки;

- request_id, полученный от партнёра;

- количество попыток;

- текст последней ошибки;

- время успешной отправки.

При ошибке задача повторяется до трёх попыток с задержками 10 и 20 секунд. После исчерпания попыток ошибка фиксируется в журнале failed jobs.

Партнёры и их адреса подключения хранятся в таблице partners. Для тестовой отправки необходимо создать активного партнёра с доступным HTTP endpoint, который возвращает ожидаемый request_id.

### Приём вебхука ###
POST /api/webhook/status
Заголовок авторизации:
Authorization: Bearer <partner-token>
Content-Type: application/json


### Пример тела: ###
{
"request_id": "a1b2c3d4",
"status": "approved",
"amount": "1500.00"
}


- 200 — вебхук обработан.
- 401 — отсутствует или неверен токен.
- 404 — отправка с указанным request_id не найдена.
- 422 — данные не прошли валидацию.


### Сводка обработки заявок 
GET /api/metrics/deliveries

Возвращает агрегированные метрики доставок заявок по текущим статусам.

#### Пример запроса:

```bash 
curl http://localhost:8080/api/metrics/deliveries \ 
-H "Accept: application/json" 
```

##### Пример успешного ответа (200 OK):
```bash
{
"successful_deliveries": 10,
"failed_deliveries": 2,
"pending_deliveries": 3
}
```

##### Поля ответа:

- successful_deliveries — количество успешных доставок.

- failed_deliveries — количество неудачных доставок.

- pending_deliveries — количество доставок, ожидающих обработки.

Все значения представлены неотрицательными целыми числами.
